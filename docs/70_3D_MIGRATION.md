# 《潮與線》2D → 3D 轉換準備

> 狀態：**B4.3 完成（0.45.0）**——使用者指定的模式（2026-10-14）：「**仿照 Google 地圖：預設是俯瞰的 2D，隨著玩家改變視角、
> 從俯瞰變成側視，3D 就顯現出來**」；10-15 追加：「**建模做完整、地形要有起伏、角色配色多樣、更像人做的**」。

> （`TL_STAGE=2d｜3d` 明寫時照它）。D1／D3／D5 因此已有答案（見 §1）；**D2、D4、D6、D7 仍照建議走，等使用者看過實物再拍板。**

## 0. 一句話

**模擬、資料、存檔、HUD、輸入邏輯全部與維度無關**（約 84% 的程式碼——runtime 64 檔、約 19,000 行裡，2D 專屬的只有約 3,000 行——且都有測試鎖住）。
只有「**舞台**」是 2D 專屬：`Stage2D`（約 1400 行）＋ `render/2d/` 的四支美術生成器（約 1400 行）。
B3.14 把這兩塊從 5316 行的 `Battle.gd` 裡切了出來，並在它們前面立了一份**契約**（`screens/battle/Stage.gd`）：
換成 3D＝**照契約另寫一個 `Stage3D.gd`**，局內畫面與全部 HUD 不必動。

**B4.0 脊椎（已做，粗糙）**：`screens/battle/Stage3D.gd`（約 450 行）——地面＋格線 shader、路徑格、礦點、橋、
節點（方塊）、導管（長條，顏色＝負載）、敵人（球）、游標與選取標記、正交相機（俯角 55°）、縮放平移。
**`Battle.gd`、覆蓋層、全部 HUD 一個字沒改**就跑得起來——蓋節點、拉導管、選取、縮放、小地圖都走原本的輸入路由：

```bash
TL_STAGE=3d TL_SHOT="C:/tmp/stage3d.png" TL_PANEL=campaign TL_LEVEL=4 TL_DEMO_TICKS=1600 <godot> --path godot --rendering-driver opengl3
TL_STAGE=3d TL_CLICKTEST=1 TL_MUTE=1 <godot> --path godot --rendering-driver opengl3      # smoke：真的合成點擊蓋出節點
python qa/check.py tests stage3d                                                         # headless 契約測試（29 條）
```

- `tests/stage3d_test.gd` 把契約的每一條寫成斷言（往返、框住全圖、縮放錨點不動、上下限、平移夾限、`center_view_on`、
  每幀同步節點／導管／敵人、`view_moved`）。**它是之後任何舞台實作的驗收尺**，也守住 `Stage3D` 不引用 autoload。
  紅得起來（把 `cell_at` 改歪 → 兩條同時倒，已驗）。
- 3D 截圖**同機器逐像素確定**（重拍兩次 0 像素差）——D7 的「同機器仍可逐像素」成立。
- **刻意沒做**的：每種節點的造型、徽章、流動珠、特效、地貌、大圖的 fit 下限（2D 的可讀性地板）、`SelfTest` 裡讀 `Stage2D`
  內部的探針。這些全是 B4.1 之後的事，而且要先等 D1–D7。

驗證過的事實（不是推測）：重構前後 **32 張截圖逐像素 0 差**、11 條 clicktest 全過、21 支 headless 測試全過
——也就是說這個接縫是真的接縫，不是紙上畫的。

## 0b. ★ B4.1 傾斜舞台（現況）

**一句話**：地面是現行的 2D 舞台（畫進一個 `SubViewport`，當貼圖貼在地上）；地形是梯田（`Relief`），建築與敵人是手作的多材質網格（`Models`），
高度乘上 `lift`——**傾斜 0° 時 lift ＝ 0、3D 不畫，看到的就是 2D 那張圖；往側面轉，地隆起、建築與敵人「長」出來**。

```text
Battle（HUD、輸入、小地圖）── 只認 Stage 契約 ──► Stage3D（傾斜舞台）
                                                   ├─ _ground：Stage2D（內嵌，畫進 SubViewport → 貼圖）  ← 地貌、格線、路徑、選取、游標、階段色調（傾斜 0° 時還包括導管、流動珠、特效）
                                                   ├─ 3D 世界：地形（Relief：頂面貼貼圖、懸崖、擺設）＋ 建築（Models.node）＋ 敵人（Models.foe）＋ 徽章（billboard）
                                                   └─ 相機：透視、窄視角（24°）、只有傾斜／縮放／平移
```

| 面向 | 做法 | 為什麼 |
|---|---|---|
| 預設視角 | **傾斜 0°（正俯瞰）**；「3D」鈕轉到 50°，再按回 0° | 使用者指定；也保住導管線寬編碼（R-3）——正俯瞰時透視等於正交 |
| 傾斜的進入點 | 左上角「3D／2D」鈕 ＋ 垂直滑桿（可點，觸控可用）；**按住右鍵上下拖**；**Shift＋滾輪** | P3：右鍵與 Shift 只是桌面便利，鈕與滑桿才是保證能用的路 |
| 範圍 | `TILT_MAX` ＝ 62°（最側視）。**旋轉（B4.4）**：左右轉動視角，任何角度全景都框得住整張圖 | D3 原本先不開旋轉；使用者 2026-10-16 要求「左右旋轉視角」，已加。透視與旋轉下導管線寬編碼的可讀性仍由 `TL_NAKED` 驗收（人判） |
| 升起 | `lift ＝ smoothstep(傾斜 / 38°)`，在頂點著色器裡乘高度 | 網格只建一次，傾斜是免費的；lift ≤ 0.012 時整個 3D 隱藏、露出貼圖裡的 2D 本尊 |
| 全景 | **每個傾斜角**下，全景（zoom ＝ fit）都框住整張圖（`_fit_view_h()` 對 4 個角二分搜尋） | 「戰役關卡一屏可見」是鎖定的設計（D4）；`stage3d_test` 逐角度驗 |
| 拾取 | 先打射線求地面交點；**傾斜後再與建築的方盒比較，先撞到誰就選誰** | 點建築的頂或側面要選到那座建築，不是穿過去之後它後面那一格 |
| 地面貼圖解析度 | 跟著**螢幕上一格有多大**分檔（0.5 一檔，1×–`GROUND_TEX_MAX`/圖寬） | 放大看貼圖不糊；分檔避免每幀重配 render target |
| 顏色 | **頂點色直接烘 `Palette` 色值**（不轉線性）＋ **烘焙光照**（受光 × 離地遮蔽，暗部偏藍） | 相容性渲染器不做 sRGB 輸出編碼；轉一次會讓建築比 2D 暗一截（量過：琥珀 (255,200,87) → (255,147,21)）；烘好的顏色讓截圖同機器逐像素確定 |
| 材質色票 | `Palette.MAT_*`／`GLOW_*`／`FOE_*`；玩家冷色＋琥珀（**琥珀仍專屬能量**）、敵人整組在品紅—紫色相帶內 | 使用者要「配色不單調」；§1.1 的兩條紀律不破：敵我一眼可分（`stage3d_test` 驗敵人色相帶） |
| 造型 | **每種各自手作的配方**（`Models.gd`）：吃同一組級數步數（出力／射速／射程／濺射），多材質拼起來；佔地與 2D 一致 | 建模完整；2D 加新節點而 3D 還沒配方 → 退回 `Extrude.glyph_mesh()`（不隱形），`stage3d_test` 要求每種都有配方 |
| 敵人 | `Models.foe()` 由**機制欄位**推導（殼、鏢、流線、發光的心、三瓣），一型四個變體（色相小幅位移）；位置與朝向問內嵌的 `Stage2D`；**動作由機制欄位推導**（`Models.foe_motion()`：重甲沉、迅捷前傾、再生有心跳、成群一跳一跳；`reduce_motion` 不動）、受擊一閃、腳下落影、受傷才有血條（B4.3） | 沒有以型別名為鍵的 `match`（§1.7）；一群同型敵人不是一個模子印出來的 |
| 地形 | `Relief.gd`：每格一個高度（梯田，地貌決定幅度）、懸崖、**敵人路徑是溝、岸是平的、橋是拱起的橋面（底下空的）**、核心與礦點是平台；頂面頂點色烘受光與遮蔽 | 格子遊戲：建築站在平的格頂，貼圖的格線不歪；起伏的單位就是格。路徑兩岸不起伏，才數得出 walk-by 的格數 |
| 拾取 | 射線沿地形步進（薄層內等距、再二分）；`to_screen()` 投影格的**頂面**；建築另以方盒比較先撞到誰 | 兩者互為反運算（往返斷言）；點建築的頂或側面選到那座建築 |

**驗證**：`tests/stage3d_test.gd`（107 條：契約、傾斜 API、每角度全景、傾斜往返、**建築拾取**、**地形拾取往返**、Camera3D 與自己的算式一致、
每種節點／敵人的造型與佔地與色階、敵人色相帶與變體、**地形的結構規則與確定性**、徽章、貼圖解析度）；`TL_STAGE=3d TL_CLICKTEST=1`（四個進入點＋傾斜下真的點擊蓋出節點）；
截圖 `stage3d_L4`（0°）、`tilt35_L4`、`tilt62_L4`、`tilt50_L1`、`tilt50_L10`、`tilt50_naked`；`qa/check.py perf` 的三列傾斜量測；
陳列照工具 `tests/gallery_shot.gd`（造型要親眼看）。

**效能**（這台機器，關 vsync，活的模擬，中位數見 CHANGELOG 0.44.0）：第 10 關 2D 4.4 ms → 傾斜 0° 5.1／50° 4.6 ms；壓力場景（547 節點）2D 19.2 → 傾斜 0° 22.8／50° 29.5 ms。

**還沒做**：① 交戰環與受威脅括號仍畫在地面（它們圍著建築的腳下，傾斜時看得到）；② 沒有即時光源與陰影（烘焙光照；只有敵人腳下的落影）；③ 雙指手勢只在平台給得出手勢事件時才有（macOS 觸控板、Android／iOS；Windows 觸控螢幕要靠鈕與滑桿），**沒有在真的觸控硬體上測過**；④ 縮放上限仍是 3 倍（與 2D 同一個契約）；⑤ **造型好不好看、地形像不像梯田、傾斜 50° 的 `TL_NAKED` 瓶頸可讀性——都是人判**（`50_QA_PLAN.md` §4.5，R-14）。

## 1. 要使用者拍板的決定

每一條：**是什麼 · 影響 · 建議**。沒有拍板之前，3D 的實作不該開始。

| # | 決定 | 影響 | 建議 |
|---|---|---|---|
| **D1** | **「3D」的範圍** | A：**3D 渲染的格子地圖**——玩法、操作、關卡、模擬一個字不改，只換呈現（建築與敵人變模型、相機有俯角）。B：**真 3D 玩法**（高度、自由視角、3D 路徑）——設計全部重來，鎖定的設計（一屏可見、橋、walk-by）都要重審。 | ✅ **已定（使用者 2026-10-14）＝ A**：模式是「俯瞰 2D → 側視 3D」，玩法與關卡一個字不改。 **A**。B 等於另一款遊戲，且會動到 `CLAUDE.md` 鎖定的設計。 |
| **D2** | **美術管線：維持「零素材、程序生成」，還是引入 glTF 模型** | 現行鎖定「所有視覺以 `_draw()` 與 shader 程序繪製，不使用外部素材」（`20_ART_DIRECTION.md` §6）：授權乾淨、體積小、改一處全同步。3D 若走程序網格（`ArrayMesh`／`CSG`）可以維持這條；走 glTF 則要有美術資產來源與授權。 | **先維持程序生成**（低多邊形＋平面著色，和現有的幾何語言一脈相承），首批只做 13 種節點＋6 種敵人。需要時再引入素材，不要一開始就改管線。 |
| **D3** | **相機** | 自由軌道相機會讓「導管線寬／顏色／徽章」這套視覺編碼失真（近大遠小），而全案的可讀性驗收（R-3，`TL_NAKED`）就押在它上面。 | ✅ **已定（使用者 2026-10-14）**：預設正俯瞰，玩家可**連續傾斜**到側視（像地圖 App）；做成透視、窄視角，傾斜 0° 時與正交相同。**旋轉（B4.4，使用者 2026-10-16 要求）已加：** 右鍵左右拖／Ctrl＋滾輪／Q、E／↺ 羅盤 ↻／雙指左右拖；`yaw` ＝ 地圖在畫面上順時針轉過的角度，0 ＝ 北在上；全景在每個角度都框得住整張圖（可讀性地板只管不旋轉也塞不進的大圖）。**（原建議：固定俯角）** **固定俯角（約 50–60°）、正交或極小 FOV 的透視、只開縮放與平移**，先不開旋轉。旋轉可以之後加（契約的 `zoom_by`／`pan_by` 不變）。 |
| **D4** | **「戰役關卡一屏可見」在 3D 下怎麼解讀** | 鎖定的設計（`CLAUDE.md` 地圖尺度）。2D 靠「固定框架＋進場自動 fit」保證；3D 沒有 `fit`，要改成「相機自動框住整張圖」。 | **維持鎖定**：進場相機自動框住整張圖（`Stage.reset_view()` 的 3D 版）。`campaign_test` 那條「fit 後填滿框架」的斷言要換成相機版。 |
| **D5** | **保不保留 2D 舞台** | 兩個舞台並存＝兩份繪圖要維護；但 2D 版是**低配機、手機、無障礙**的退路，也是回歸比對的基準。 | ✅ **已定**：2D 舞台不是退路而是**地面本身**（傾斜舞台內嵌它），所以兩者不會漂；玩家實玩預設傾斜舞台，`TL_STAGE=2d` 回到純平面，自動化預設平面。 **轉換期並存**（設定裡一顆開關）；3D 穩定後再決定要不要留。契約讓兩者並存幾乎零成本。 |
| **D6** | **效能與平台底線** | 現行壓力情境（547 節點、2045 導管、200 敵人）渲染約 23 FPS（RG-8，別台機器）；**這台機器修好量法後實測 220 ms／幀（約 5 FPS，RG-183）**。3D 的導管若逐條一個 `MeshInstance3D` 會更糟；手機移植的門檻也會更高。保持 `gl_compatibility`。 | **導管、節點、敵人一律走 `MultiMesh`（一種一個 draw call）**，流動珠用 shader 的 UV 捲動而不是逐珠物件。**效能預算要在 B4.0 就量，不要留到最後**（見 §6）。 |
| **D7** | **回歸比對怎麼辦** | 2D 截圖「同機器逐像素相同」；3D 的光柵化在不同 GPU／驅動上不保證位元相同。 | 同機器仍可逐像素；跨機器改用**容忍度比對**（`qa/check.py shots` 的 `_compare` 加一個閾值參數）。 |

## 3. 接縫：`Stage.gd` 契約

`screens/battle/Stage.gd` 是一個 `Control` 基底類別，**每一個函式都是空實作加文件**——它就是 3D 舞台的待辦清單：

| 類別 | 契約 | 2D 的做法 | 3D 的做法（建議） |
|---|---|---|---|
| 投影／拾取 | `cell_at(螢幕)`、`point_at(螢幕)`、`center(格)`、`to_screen(地圖座標)`、`in_map(格)` | `(pos − map_origin) / zoom` | **射線與地平面（y=0）求交**；`to_screen` ＝ `camera.unproject_position()` |
| 視野 | `reset_view()`、`zoom_by()`、`pan_to()`、`pan_by()`、`center_view_on()`、`tick_view()` | `zoom`／`pan` 兩個標量、`draw_set_transform` | 相機高度／目標點；`reset_view` ＝ 自動框住整張圖（D4） |
| 讀值 | `zoom`、`fit`、`pan`、`pan_goal`、`FRAME`、`ZOOM_STEP` | 同左 | `zoom/fit` 比值給 HUD 的「全景 100%」；`FRAME` ＝ `SubViewportContainer` 的矩形 |
| 視野查詢 | `view_world_rect()`、`oversized()` | 直接算 | 相機視錐與地面交集的外接矩形 |
| 每幀推導 | `engaged`、`threat`（HUD 與小地圖會讀） | `_draw()` 開頭用 `Combat.engaged()` 算 | **同一份算式，搬到 `_process`**——這兩個與畫法無關 |
| 訊號 | `view_moved` | 視野變了就發 | 同 |

三個約定（寫在契約檔頭）：

1. **座標**：「格」＝ `Vector2i`（模擬層唯一座標）；「地圖座標」＝ 格 × `Shapes.GRID`（像素）；「螢幕座標」＝ `Control` 的全域像素。3D 世界座標建議 `Vector3(格.x, 高度, 格.y)`（1 格 ＝ 1 單位）。
2. **舞台只讀 `s`**（`SessionState`），不改局面、不擁有規則。
3. **它是滿版 `Control`、`mouse_filter = IGNORE`**——點擊一律落到 `Battle._gui_input`（B0.7.2 的教訓：命中區與繪圖是兩件事）。3D 版把一個 `SubViewportContainer`（同樣 IGNORE）放在裡面。

**`Battle._build_modules()` 是主畫面裡唯一知道「哪一種舞台」的地方**：`Stage3D.new() if Hooks.stage3d else Stage2D.new()`。
要把它做成玩家的設定（D5），改的就只有這一行判斷。

## 4. `Stage2D` 的每一層 → 3D 對應

Stage2D 的 `_draw()` 依序畫下面這些層（都讀 `s`，不改 `s`）。3D 版每一層一個節點，**由資料驅動重建／更新，不逐幀 new**。

| 2D 層（`Stage2D._draw_*`） | 內容 | 3D 做法（建議） |
|---|---|---|
| 地貌（`terrain_layer`＋`Terrain.build()`） | 八種地貌：底色＋裝飾（B3.13），**只在換圖時重畫** | 地面一塊 `MeshInstance3D`（程序貼圖／頂點色）＋裝飾 `MultiMesh`。`Terrain.build()` 的零件是純資料（位置、種類、種子），**可以直接當 3D 的輸入** |
| 網格線 | `Shapes.draw_grid` | 地面 shader 的格線 |
| `_draw_path` | 侵蝕暈（＝walk-by 傷害半徑）＋路徑帶＋來襲箭羽＋橋 | 地面上的 decal／貼花網格；**暈的外緣要保持「走格線、可數格」**（`20_ART_DIRECTION.md` §1.6：規則層要讓玩家用格子數邊界） |
| `_draw_ore_cells`、`_draw_fields` | 礦點、光環／射程場 | 地面圓環 decal |
| `_draw_conduits` | 導管：**線寬＝流量、顏色＝資源／飢餓、流動珠＝方向**（R-3 的核心編碼） | 一條導管一個管狀網格實例（`MultiMesh`），**寬度與顏色走 per-instance 參數**；珠子用 shader UV 捲動。**這是可讀性風險最大的一層**（D3） |
| `_draw_nodes` | 13 種節點，每種有自己的體積語言（`Glyphs.build_for()`）＋三態徽章＋交戰高亮 | 每種節點一個程序網格（低多邊形）＋徽章用 `Sprite3D`／billboard。`Glyphs` 的規格表（哪種形狀、幾何體積）可以直接當 3D 網格的設計稿 |
| `_draw_enemies` | 六隻敵人（`Foes.build()`，由機制欄位推導） | 六種程序網格；位置用 `Tide.pos_of()`（模擬層給的連續座標，**不要在 3D 重算**） |
| `_draw_shots`、`_draw_bursts`、`_draw_shields`、`_draw_ripple` | 開火兩端、碎片爆、屏障擋格、開打漣漪（0.2 秒、十幾像素的東西） | 短壽命的 `GPUParticles3D`／immediate mesh。**`Motion.reduce` 時一律不生成**（`reduce_motion` 的承諾，§4.4） |
| `_draw_selection`、`_draw_hover`、`_draw_connect_guides` | 選取框、擺放預覽（畫那隻角色本人）、拉線導引 | 外框 shader／decal；擺放預覽用同一套節點網格半透明 |
| `_draw_frame_matte` | 把超出框架的地圖遮掉 | **不需要**——`SubViewportContainer` 自己就是框架 |
| 階段色調 | 戰鬥期整層淡橙、準備期淡青（`10_GDD.md` §6.2 硬性要求 4） | 後處理或地面 tint |

**不要重新發明的東西**：`Glyphs`／`Foes`／`Terrain` 的輸出都是**純資料的零件清單**（位置、種類、色值 token），2D 的 `paint()` 只是「怎麼把零件畫成多邊形」。3D 版應該**吃同一份零件清單**、換一個「怎麼把零件變成網格」，而不是重新從 `NodeDefs` 推一遍——否則兩套會漂。

## 5. 輸入與相機

- **拾取**：`cell_at()`／`point_at()` 是 `Battle._gui_input` 唯一的座標來源。導管命中靠 `point_at()`（格為單位的浮點座標）＋ `WIRE_PICK = 0.3`；3D 的透視會讓這條帶在螢幕上的寬度隨距離變化——D3 選正交／極小 FOV 就避開這個問題。
- **平移**：中鍵拖曳走 `stage.pan_by()`（契約）。觸控沒有中鍵，**手機移植要補雙指手勢**（風險已登記在 `40_PRODUCTION_PLAN.md`，與 2D 無關）。
- **觸控命中 ≥ 44×44 px**：HUD 已全部遵守（`UiKit.touchable`）；3D 地圖上的點擊目標（一格 32px × zoom）仍是「放大操作」解，與 2D 同。
- **相機緩動**：`tick_view(delta)` 用 `1 − exp(−k·dt)`（與幀率無關）；`reduce_motion` 時一律直接到位。

## 6. 效能預算（B4.0 就要量）

| 情境 | 2D 現況（`TL_STRESS=1`，渲染） | 3D 目標 |
|---|---|---|
| 一屏戰役關 | **第 1／5／10 關（7／25／29 節點）實測 7.3／18.3／21.3 ms ＝ 138／55／47 FPS**（`TL_STRESS=1 TL_PANEL=campaign TL_LEVEL=N TL_DEMO_TICKS=2500`，RG-184）——第 10 關已貼著 45 FPS 底線，其中 `_draw_path` 的 3.3 ms 是靜態內容卻每幀重算 | ≥ 60 FPS（桌面）、≥ 45 FPS（底線）。3D 版的基準就是這三個數字 |
| 壓力情境（547 節點、2045 導管、200 敵人） | 別台機器約 23 FPS（RG-8）；**這台機器 220 ms／幀、最壞 279 ms（約 5 FPS，B3.14 修好 `TL_STRESS` 的量法後實測，RG-183）**——`_draw` 的 CPU 時間約 176 ms | 不得比 2D 差；`MultiMesh` 應該更好。**這是整個 3D 計畫的第一個效能債，不是 3D 才有的** |

量法不變：`TL_STRESS=1`（模擬凍結、只量渲染）。**3D 版也要吃這個鉤子**——它是 `Hooks.stress`，與舞台無關。
