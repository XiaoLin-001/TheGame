# 《潮與線》美術方向

> **視覺／動效／音訊的唯一權威。** UI 一律引用本文件的 token，不得硬編碼新色值或新間距。
> 上位文件：`00_CONCEPT.md`、`10_GDD.md`。
> 狀態：**v0.2**（新增 §1.6 地圖元素視覺語言含跨越點；HUD 改浮層；一致性檢查加 `TL_NAKED` 檢定）　|　最後更新：2026-07-27

---

## 0. 核心視覺命題

> **有機混沌（敵潮） vs 幾何秩序（你的線）。**

這不是裝飾性的風格選擇，而是**把遊戲主題直接畫出來**：玩家建造的一切都是**直線、正圓、銳角、對齊網格**；敵潮則是**曲線、不規則、脈動、不對齊**。玩家看著自己的秩序被混沌侵蝕，再把它重建回來——這正是核心循環的情緒。

這條命題支配以下所有決策。任何新增視覺元素都必須回答：**它屬於秩序還是混沌？**

| | 秩序（玩家） | 混沌（敵潮） |
|---|---|---|
| 形狀 | 正圓、正方、等邊多邊形 | 不規則凸包、水滴、鋸齒 |
| 線條 | 直線、90°/45° 轉折 | 貝茲曲線、抖動 |
| 對齊 | 嚴格對齊 32px 網格 | 完全不對齊 |
| 動態 | 恆定速率、線性或 ease-out | 呼吸式脈動、隨機微抖 |
| 色相 | 青／琥珀（冷靜、機械） | 品紅／紫（有機、危險） |

**配色紀律**：
- 全遊戲**只有敵人與危險狀態能用品紅／橙**。這保證玩家的眼睛永遠能在混亂的畫面裡瞬間找到威脅。
- 琥珀色**專屬於能量**。看到琥珀＝跟耗能有關。這是本作最重要的資訊通道（能量＝取捨的化身）。

### 1.3b 手機移植預留條款（從第一批就生效）

Windows 先行，但事後補觸控支援極痛，故以下四條在每批 UI 一致性檢查中稽核：

| # | 條款 |
|---|---|
| P1 | **版面全部可縮放**。以 16:9 為基準，但**不得硬編碼像素位置**——一律用錨點、容器與比例。 |
| P2 | **所有可點元素的觸控命中區 ≥ 44×44 px**（視覺可以更小，命中區不行）。 |
| P3 | **操作不得只靠 hover／右鍵／鍵盤快捷**。這些可以有，但每個功能都必須有一條純點擊／拖曳的途徑。 |
| P4 | **關鍵資訊不得只靠 tooltip 呈現**（觸控裝置沒有 hover 態）。 |

**P2 的直接後果（2026-07-27）**：局內 HUD 從三欄式改為**全畫面地圖 ＋ 浮層／抽屜**（`10_GDD.md` §6.2）。固定窄欄塞不下 9 個 44×44 px 的建造項目，硬塞就會犧牲 P2 或犧牲地圖面積。浮層還必須**可收合**，收合後地圖 100% 可見。

### 1.4 圓角與線寬

| Token | 值 | 用途 |
|---|---|---|
| `radius.none` | 0 | **遊戲內所有玩家建築**（秩序＝銳角） |
| `radius.ui` | 2 | UI 面板與按鈕（僅此一種） |
| `stroke.hair` | 1 | 分隔線、網格 |
| `stroke.base` | 2 | 節點外框、UI 邊框 |
| `stroke.emphasis` | 3 | 選中、聚焦 |

**導管線寬為動態值**：`width = 2 + 6 × (flow / 最大cap)`，範圍 2–8px。這是遊戲最重要的資訊視覺化——**線的粗細就是流量**。

> **★ 分母是全遊戲的最大 cap，不是這條線自己的**（B1.1.1 改）。原本的分母是自己的 cap，也就是飽和度——那讓**加粗一條線會讓它變細**（分母變大），而按鈕就叫「加粗」。使用者實看後的原話：「有時候升級的管道卻比沒升級的還小」「應該要是越大的流量管道越粗」。
>
> 順帶修掉的是**兩個通道在講同一件事**：線寬與顏色原本都由 `flow / cap` 驅動，等於重複一次飽和度，而「這條線實際搬了多少」沒有任何通道在講。現在**線寬＝絕對流量、顏色＝飽和度**，各講一件事。
>
> 代價：顏色因此必須改成**連續**的（原本是「滿了才亮」的兩段跳）——飽和度只剩這一個通道，兩段跳會讓九成滿和一成滿長得一樣。用 `sat²` 而不是線性，保住「第一台發電機讓那條線當場亮起來」那個 B0.3 的教學瞬間。

#### 1.4a 流動珠（★ B0.6.1 新增）

**問題**：線寬與顏色說的是「這條線有多滿」，**沒有一個元素在說「東西正在動」**。一張靜態的粗線和一張靜態的細線都不會動，玩家看到的是一張接線圖，不是一條產線。使用者實看 B0.6 的畫面時的原話：「看不到貨物流動的感覺」。

**做法**：導管上跑一列小珠子。

| 屬性 | 規則 | 為什麼 |
|---|---|---|
| **顏色** | 礦砂 `text.primary`（近白）／能量 `energy.amber`／合金 `alloy.violet` | 三種資源靠**色相**分開：無色相／暖／冷紫。沿用配色紀律 2（琥珀專屬能量）。同一條幹線同時走多種資源時，看得出**誰往核心走、誰往塔走** |
| **對比** | 每顆珠子先畫一圈 `bg.deep` 底，再畫亮色芯 | 導管本身就是亮青，亮青珠子畫在亮青線上等於沒畫。**深色底是這個元素能被看見的唯一原因** |
| **多列並行** | 礦砂 −、能量 ＋、**合金恆走中線**，沿線垂直偏移 ∓(線寬×0.45+1)px；只有一種資源在跑時全部走中線 | 疊在一起會互相蓋掉，也讀不出不同資源方向不同。細線上硬要分排會讓珠子懸在線外，看起來像掉出來的東西 |
| **速度** | ∝ 該資源的流率（單位/秒），固定間距 16px | 幹線 20/秒的珠子明顯跑得比支線 6/秒快。**速度是第三個獨立通道**，與線寬（飽和度）、顏色（狀態）不重複 |
| **方向** | 該資源的**淨流向**（解算器兩條有向邊之差） | 導管無方向（`10_GDD.md` §7.2），方向是每 tick 解出來的結果，不是玩家設定的屬性 |
| **停止** | 流率 < 0.05 就完全不畫 | 沒在流動的線必須是靜止的——這是「哪裡斷了」最快的讀法 |

> **★ 這不是實體物品搬運。** 珠子是**渲染層**由已解出的流率推出來的，模擬層一無所知（`10_GDD.md` §3.1 鎖定：流量網路，非物品實體模擬）。珠子的位置由 `tick_count` ＋ 幀內插值推算，**不是被搬運的物件**，不參與任何判定。這條界線不得越過——一旦珠子變成有位置有狀態的實體，`O(物品數)` 的效能與確定性負債就回來了。

> **`reduce_motion`**：開啟時珠子停止移動但**仍然畫**（位置固定在起點側），流量資訊靠線寬與顏色承載，不因關動效而丟資訊。設定畫面在 B1.4，實作與驗收排 **B1.6**。

**★ 為什麼合金珠不是 `alloy.steel`**（B1.1 定案）：鋼銀 `#b8c9d4` 的明度和導管的青 `#7fd4e8` 幾乎一樣，而珠子是畫在導管上的——鋼銀珠會直接融進線裡，重演 B0.6「看不到貨物流動」那個缺陷。**建築的顏色和它產出的資源的顏色本來就不是同一件事**：採集器是青色而礦砂珠是近白，熔爐是鋼銀而合金珠是紫，同一條慣例。

**升級刻度改為垂直短刻線**（原為圓點）：圓點會和流動珠混成同一個東西，而它們的語意相反（一個是固定的線材等級，一個是變動的流量）。**同一個形狀不得表達兩件會同時出現的事。**

### 1.5 網格

地圖網格 **32px**。所有玩家建築嚴格對齊。網格線用 `border.subtle` 於 1px，透明度 20%。

### 1.6 地圖元素的視覺語言（★ 新增）

| 元素 | 畫法 | 為什麼 |
|---|---|---|
| **敵人路徑** | `tide.deep` 的低透明度帶狀底色 ＋ 不對齊網格的抖動邊緣 | 它屬於**混沌**側。玩家一眼看出「這條帶子不是我的」 |
| **來襲方向**（★ B0.7） | 沿路徑每 4 格一個 `tide.magenta` 低透明度**箭羽**，指向行進方向 | 一條帶子只說「這裡是路」，**沒說潮從哪邊來**。空地圖上這是新玩家的第一個問題，而它決定所有擺位。順著箭羽走也就找到了核心——一個元素答兩題（`50_QA_PLAN.md` §4.4）。**靜態不動**：會動的東西在混沌側已經有敵人本體了，路面再動會搶掉真正該被注意的東西 |
| **跨越點（橋）** | 路徑帶之上的一段**架高結構**：`order.cyan` 的雙線橋面 ＋ 兩端 45° 引道 ＋ 橋下留可見的路徑帶陰影 | ①「架高」必須用畫的說清楚——它是**橋上導管不受攻擊**這條規則的唯一解釋（`10_GDD.md` §3.2）。玩家看到它跨在上面，就不會問「為什麼這段打不到」。②它屬於**秩序**側，是玩家可用的動線 |
| **礦點** | `order.dim` 的空心正圓，蓋上採集器後填實 | 秩序側，可用資源 |
| **核心** | 最大的幾何體，`order.bright` 描邊；受擊時整體閃 `warn.orange` | 唯一會讓敵人駐足的目標，必須最顯眼 |
| **潮鳴的場**（★ B1.8） | 交戰時，在**實際射程半徑**（5 格＝160px）畫一圈 `order.cyan` 低透明度脈動細環；同時被它影響的敵人**輪廓描一圈 `order.cyan`** | **它是全案唯一一座不開火的塔**（`rof = 0`），所以沒有開火線、沒有開火音——B1.7 之前它每秒吃 9 能量而畫面上一個回饋都沒有，玩家無從確認它在工作。這是本作最不能藏的一件事：「塔在交戰時每秒吃電」就是核心取捨本身。<br>**為什麼不是給它一個開火音**：它的動作是「場」不是「擊」，硬配一個打擊音是在說謊。<br>**為什麼標在敵人身上**：減速 −40%／破甲 −25% 作用在敵人身上，標在敵人身上因果才讀得出來——標在塔上只說得出「它開著」。<br>**形狀怎麼分得開**（§4.3b 那條規則）：場環半徑 160px vs 交戰環 15px，差一個數量級；敵人輪廓是**閉合折線**，與血量弧（`tide.deep` 圓弧）一個是線一個是弧 |

**浮層的硬性要求（★ B0.7.4）**：一律走 `UiKit.panel(opacity)`——近乎不透明的 `bg.panel` 底 ＋ `border.strong` 細邊 ＋ `radius.ui`，且**建構子就把 `mouse_filter` 設成 `IGNORE`**（浮層是資訊，不是障礙物）。兩條由使用者實玩逼出來的規則：

1. **不透明度不是風格選擇。** 預設的半透明面板讓導管從字後面穿過去，暗色的次要文字直接讀不到。要「看得見底下」的浮層（角色簡介）才降到 0.88，其餘一律 0.96。
2. **會隨內容改變尺寸的資訊面板 ＝ 讀不了的面板。** 列數與寬度必須固定，沒有值的列留在原位變暗，不得隱藏——隱藏會讓下面每一列往上跳。**位置固定本身就是可讀性**：玩家記得「淨值在第八行」，那一行就不該跑。

**硬性要求**：**跨越點必須在不縮放、不 hover 的狀態下一眼可辨**（`10_GDD.md` §3.2）。玩家不該靠試錯才知道哪裡能鋪管——那是浪費 45 秒準備期的操作成本（R-1）。

### 1.8 大圖導引：小地圖與邊緣箭頭（★ B2.1b）

只在**地圖大過框架**時出現（無盡）。戰役全部一屏可見，問題節點就在畫面上，多一個浮層只是多一塊遮擋。

| 元素 | 畫法 | 為什麼 |
|---|---|---|
| **小地圖底** | `bg.panel` 0.96 不透明 ＋ `border.strong` 細邊，貼框架**右下角**內側 | 浮層硬性要求（§1.6）。右下角是離建造欄（左）與能量列（上）最遠的角 |
| **路徑** | `tide.deep` 實線 | 與主畫面同一個編碼，不另發明 |
| **玩家節點** | `order.cyan` 1px 點 | 小地圖上讀的是**產線的形狀**，不是個別節點 |
| **問題標記** | `warn.orange` 方點，**比節點點大一倍** ＋ 脈動 | 橙＝危險通道（§1.1）。大一倍是因為它要在一堆青點裡被一眼挑出來 |
| **視野框** | `order.bright` 1px 空心矩形 | 「我在哪」——這是小地圖與「一張縮圖」的唯一差別 |
| **邊緣箭頭** | 框架內緣的 `warn.orange` 三角，指向畫面外的問題；最多 **3 個** | 打斷式通知。**上限 3 個**是反模式清單「資訊過載」的直接套用——十個箭頭等於沒有箭頭 |

**兩者都可點，點了把視野移過去。** 命中區 ≥ 44×44 px（P3 手機移植預留條款）。這也是大圖平移目前唯一的**純左鍵**動線——中鍵拖曳在觸控上不存在（R-16）。

**小地圖不畫敵人。** 敵人是路徑上的行進物，位置由路徑決定；把它們畫進去只會讓小地圖每一幀都在閃，而玩家從中得不到任何**決策**（他不能改變敵人的路線）。小地圖回答的是「我的產線長什麼樣、哪裡壞了」。

### 1.7 敵人輪廓與開火形態（★ B1.6.3）

> 起因：使用者實玩回報「**所有敵人都長一個樣，根本看不出差異**」「塔的攻擊可以有更多不同的特效嗎」。
> 查證屬實——三種敵人畫的是**同一個 9 邊形、同一個 `tide.magenta`**，只有半徑不同；五座塔的開火畫的是**同一條 `order.bright` 直線**。

#### ★ 統御規則：視覺由**既有數值**推導，不新增美術資料

每一個視覺特徵都掛在 `Enemies.DEFS`／`NodeDefs.DEFS` **已經存在**的機制欄位上，不新增 `shape` / `fx` 之類的美術欄位。三個理由，由重到輕：

1. **設計上不可能說謊**——沒有辦法做出一隻「有護甲但看起來不硬」的敵人。屬性就是外觀。
2. **M3 擴到 18 種敵人、24 隻角色時自動正確**（`10_GDD.md` §5 內容矩陣），不必逐一補美術欄位，也不會漏。
3. 少一張要跟著資料表一起維護的對照表。

#### 敵人：三種**明度結構**（全部仍屬**混沌**側——不規則、脈動、不對齊）

| 觸發條件（既有欄位） | 畫法 | 讀出來是什麼 | 現況命中 |
|---|---|---|---|
| 預設 | **9 邊柔性水滴**，wobble ±15%，`tide.magenta` 單一階 | 基準、軟 | 漂蟲 |
| `armor > 0` | **6 邊硬稜角**，wobble ±7%，加一圈 `tide.deep` 3px **同形鎖邊＝甲板** | 有殼、硬、**物理打不動** | 甲殼（armor 8） |
| `speed > 1.2` | **垂直行進方向壓扁**（×0.55）＋ 中心一顆 `tide.bright` **亮核心** | 快、薄 | 熾泳（speed 1.6） |

> **★ 這張表是實看 A/B 改過三次的結果，前兩版都被否決**（B1.6.3）。留著這段，因為它是「特效不能只在腦裡設計」的直接證據：

**① 拖尾被否決。** 第一版給高速敵人兩個遞減殘影。第 5 波的間距是 **0.6 格**，殘影落在後面那一隻身上——一列 11 隻分得開的敵人糊成一條連續的香腸。把「看不出差異」修成了「看不出有幾隻」。

**② 沿行進方向拉長也被否決。** 砍掉拖尾之後改拉長本體，A/B 顯示問題**完全一樣**：在單列縱隊裡，任何沿行進軸變長的東西都會碰到鄰居。

→ 結論寫成規則：**敵人的差異化只能用「不增加行進軸footprint」的手段**——壓扁（footprint 只會變小）、換頂點數、換明度。

**③ 輪廓在 fit 倍率下不夠用。** 敵人在 fit 倍率只有 **16–24px**。六邊形勉強讀得到，壓扁幾乎讀不到。**明度差活得下來**，所以三種各給一個明度結構：軟＝單一階、硬＝加暗鎖邊、快＝加亮核心。這是 `tide.bright` 這個 token 存在的唯一理由。

**為什麼甲板是「同形鎖邊」而不是外圈弧**：血量弧已經是 `tide.deep` 的圓弧、畫在 `r+4`（B0.6）。再加一圈外弧就是**同一個位置上的兩個訊息**，而 §4.3b 那條規則說「換顏色不夠，要換形狀」——這個專案已經在這裡踩過兩次（B0.6 儲槽充能弧撞血條、B1.6 受擊環撞交戰環）。鎖邊貼在輪廓上、亮核心在正中心，和任何弧都不會疊。

**為什麼亮核心不用橙**：橙是「建築受損／能量不足」的通道（§1.1）。熾泳的名字雖然是「熾」，但把橙放到敵人身上會讓玩家的警示通道多一個假訊號。亮階留在品紅色相內。

**barrier（能量抗性）刻意不另給視覺通道。** 三個結構已經解掉「看不出差異」；再疊第四個訊息在一顆 16px 的東西上會回到反模式清單的「資訊過載」。精確的抗性數字在**圖鑑**裡。

#### 塔的開火：四種形態（全部屬**秩序**側——直線、正圓、青系）

| 觸發條件（既有欄位） | 畫法 | 讀出來是什麼 | 現況命中 |
|---|---|---|---|
| 預設（`dmg_type = physical`） | **短促實心彈丸**沿線飛行（不是整條線亮起），`order.cyan` | 物理＝有質量的東西飛過去 | 錨 |
| `pierce` | **整條貫穿光束**一次亮到底，`order.bright`，寬度 3→1 衰減 | 能量＝瞬間、整條線上的都被打到 | 稜鏡 |
| `splash > 0` | 彈丸 ＋ 命中點一圈**擴張環**，半徑 ＝ 資料裡的 `splash` 格 | 濺射範圍**有多大**（原本玩家完全看不到） | 碎浪 |

| `reclaim > 0` | 細彈丸 ＋ 命中後一顆 `energy.amber` 珠**回流到塔** | 它把價值換成**能量**送回電網 | 回收者 |

**物理 vs 能量用形狀分，不用顏色分。** 琥珀專屬於能量這個**資源**（§1.1 配色紀律），拿它去畫「能量傷害」會污染本作最重要的資訊通道——玩家看到琥珀必須永遠是「跟耗能有關」。所以：**彈丸＝物理、光束＝能量**。回收者那顆珠是全域唯一的例外，而它是對的——那顆珠真的是能量，正在流回電網。

**★ 濺射環只掛在一發上。** 碎浪是「**一發**濺射打中 N 隻」，而模擬層為了記傷害會產生 N 筆命中記錄——照著畫就是 N 個同心圓，既吵又把機制講錯（實看抓到）。圓心是**主目標那一格**，不是每一隻。

**潮鳴不在此表**：它 `rof = 0`、不開火，回饋是 B1.8 的場環（§1.6）。

**★ 驗收這一節必須用 `TL_FOCUS` 近照，而且要挑 `ttl` 走到一半的那一格。** 開火特效只活 3 個 tick（0.3 秒），`TL_SHOT` 凍結在剛發射那一格時濺射環半徑是 0——**畫面上什麼都沒有，看起來就像沒做**。這是 RG-100（脈動元素要在波谷驗收）的同一類陷阱。

## 4. 動效原則

### 4.1 時長階

| Token | 時長 | 用途 |
|---|---|---|
| `dur.instant` | 0.12s | 按鈕回饋、hover、選中框 |
| `dur.base` | 0.24s | 面板開闔、數值補間、狀態切換 |
| `dur.slow` | 0.50s | 畫面轉場、局末結算逐項揭示 |
| `dur.ambient` | 2.0s+ | 敵潮脈動、背景呼吸（循環） |

### 4.2 緩動

- **玩家操作的回饋**：`ease-out-cubic`（快起慢收＝有回應感）
- **系統自動的變化**（資源數字、流量粗細）：`linear`（＝機械的誠實，不誇張）
- **敵潮的動態**：`ease-in-out-sine` 循環（＝有機的呼吸）

### 4.3 什麼動、什麼不動

| 一定要動 | 一定不動 |
|---|---|
| 導管粗細（隨流量即時變化） | 網格 |
| 能量條（含警示脈動） | 已放置節點的位置 |
| 敵人本體（脈動＋前進） | UI 面板容器 |
| 波次倒數最後 10 秒（數字脈動） | 文字（不做打字機效果） |
| 建造預覽（半透明幽靈） | 背景（不做視差） |

### 4.3b 實作狀態（★ B1.6）

**時長階與緩動的實作在 `scripts/render/Motion.gd`**（B1.6 才建立——它從第一批就列在 `CLAUDE.md` 的目錄樹裡，但一直不存在，於是每個動效都是散在畫面層的字面量）。全專案的脈動、效果壽命、碎片方向一律走它。

兩條紀律：

1. **一律由 tick 驅動，不用系統時間。** 渲染可以不確定，但別引入新的亂數源——`TL_SHOT` 凍結在第 N tick 時，同參數要拍出同一張圖。
2. **碎片與閃光是純渲染，不進 `state_hash()`。** 它們由模擬層在擊殺與清殘骸時生成（那兩個時刻只有模擬知道），但不參與任何判定。

已實作：碎片爆（擊殺／建築被毀）、正在被啃的四角括號、倒數最後 10 秒脈動、敵潮呼吸、能量條警示脈動。**未實作**：局末結算逐項揭示（`dur.slow`）、色彩層次校準。

**★ 一條從兩次錯誤裡長出來的規則**：**同一個位置上的兩個訊息，換顏色不夠，要換形狀。** B0.6 的血條與儲槽充能弧都是琥珀圓弧、B1.6 的受擊環與交戰環都是橙色圓環——兩次都是截圖當場才抓到。節點上要加任何新指示，先問「它和既有的那幾個形狀分得開嗎」。

### 4.4 可跳過原則

**所有動效都可跳過。** 設定裡提供「減少動態效果」開關（一併關閉脈動、閃光、轉場），這既是無障礙需求，也是高手快速重來的需求。局末結算的逐項揭示可按任意鍵直接跳到底。

## 6. 素材生產管線

### 6.1 全程序繪製，零外部圖檔

**決策**：所有遊戲內視覺元素以 Godot 的 `_draw()` API 與自訂 shader **程序繪製**，不使用任何外部 PNG／SVG 素材。

**理由**：
1. 極簡幾何風格的元素本來就是圓、線、多邊形——用繪圖 API 表達比用貼圖更自然。
2. 任意解析度下都銳利（向量本質），不需要多套解析度資產。
3. 導管粗細隨流量即時變化，本來就必須是程序繪製。
4. exe 體積可控（目標 < 80MB），且無授權疑慮。
5. 調色只需改一處 token，全遊戲同步。

**例外**：字型（SystemFont，系統提供）。

**★ B1.5：音訊也走同一條。** 音源不是外部素材，是 `assetgen/gen_audio.py`（純 Python
標準庫，零相依）算出來的——**那支腳本才是音源的原始碼，`.wav` 是它的輸出**。
要調音色改腳本再跑一次，不要去修 wav。
匯入一律 `compress/mode=0`（PCM）：Godot 預設的 QOA 是有損壓縮，壓過之後連
「這個檔案有幾個取樣」都問不到，循環接點更無從驗起。

### 6.2 命名與目錄慣例

```
godot/
  assets/
    audio/
      bgm/       tl_bgm_<場景>_<層>.wav      例：tl_bgm_battle_perc.wav
      sfx/       tl_sfx_<類別>_<動作>.wav    例：tl_sfx_build_place.wav
  scripts/
    render/      Palette.gd    ← 本文件 §1 的 token 實作，唯一色值來源
                 Shapes.gd     ← 共用繪圖函式（節點、導管、敵潮輪廓）
                 （時長與緩動常數暫時只活在本文件 §4——B0.1 建的 Motion.gd
                   到 B1.1 為止零呼叫者，已刪；B1.6 做動效時再建它用得到的部分）
```

**硬性要求**：`Palette.gd` 是全專案唯一的色值來源。任何 `Color(...)` 字面量出現在其他檔案，視為缺陷。
